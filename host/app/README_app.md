# PC 端以太网音频（ZYNQ 7020 · 领航者）

板子（ZYNQ XC7Z020 + PL 侧 YT8531C 千兆 PHY + Xilinx TEMAC，强制 100 Mbps 全双工）通过网线
直连 PC，用**广播 UDP** 双向传音频：

```
板载麦克风 → I2S → PL → DMA → DDR → UDP 50505 → PC（本程序播放 + 显示统计）
PC（WAV/测试音）→ UDP 50506 → 板子 DDR → DMA → I2S DAC → 耳机口播放
```

本目录是 PC 端程序，只用 **Python 标准库 + numpy + sounddevice**（不需要 pip 装新东西）。

> **v3.0 起界面改成网页**（`web/index.html` + `web_server.py`），用浏览器 `--app` 模式开独立窗口，
> 不再依赖 tkinter。启动方式、5 页结构、打包成 EXE 的步骤与三个打包坑，见
> **`web/README-web.md`**。旧的 tkinter 版 `app.py` 保留可用（`python app.py`）。

## v1.3 新增：一键 A/B + 自动报告（**答辩用**）

听感对比只有现场的人能感受到，评委只会问"到底安静了多少 dB"。现在点一下按钮：

1. 依次切到 **旁路 → 轻量门 → RNNoise**，每档先稳定 1.5 s 再测 8 s；
2. 每档采集 帧率 / 丢帧 / 欠载 / 溢出 / RMS / 噪声底(p10) / 语音峰值(p95)；
3. 存一段该档的 WAV；
4. 落一份 **markdown 报告**（表格 + 自动结论 + 音频文件名）到 `recordings/`。

约 30 秒拿到"能直接贴进比赛文档的表"和"能放给评委听的三段音频"。

> 指标口径写在报告抬头里，可复现：噪声底 = 50 ms 帧 RMS 的 p10（语音只占小部分时间，
> 所以 p10 落在背景噪声上）；抑制量 = 旁路噪声底 − 该档噪声底。
> 实现见 `ab_report.py`。


### 界面怎么用

1. **① 收听板载麦克风**：选「输出声卡」→ 点「刷新」→「开始收听」。
   收 50505，重组成 10 ms 帧，经抖动缓冲用 `sounddevice.RawOutputStream`
   （48 kHz / 2 ch / int16 / 块 480 样本）实时播放。
   统计：帧率、已收帧、丢帧、缓冲深度、欠载、溢出/修剪、重复/乱序、非法包、
   目标/抖动（自适应目标 · 实测到达抖动）、漂移/修正（ppm · 删插样本次数）、隐藏帧；
   两条进度条是当前输入电平（RMS 与 dBFS）和峰值。
2. **波形 / 频谱**：左边滚动 2 s 波形（每列画 min/max），右边 64 段对数频谱
   （40 Hz~16 kHz，柱越高越响，超过 85% 变红，橙色线是缓慢衰减的峰值保持 ~6 dB/s）。
   两个画布由主线程 25 fps 刷新，从 4 s 环形缓冲取数据，**不与音频回调抢锁**；
   没信号时也在刷新，不会闪。
3. **录音 / 增益**：「开始录音」把**正在播放的内容**（含增益、含补的静音）写成
   `recordings/mic_YYYYmmdd_HHMMSS.wav`，按钮旁显示已录秒数；再点一次停止并回显文件名。
   「增益 A/B」在 1.0× / 2.0× 之间切，现场演示"能听出差别"（切的是播放增益，不改缓冲）。
4. **② 推送到板子**：目的地址默认 `255.255.255.255`、端口 `50506`。
   「选择 WAV…」→「发送 WAV」：任意采样率/位深/声道都行，程序自动转 48 kHz / 16 bit / 立体声，
   按 **100 帧/秒**推送；「发送测试音 440Hz/10s」不用文件，适合现场演示。
   进度条显示已发送秒数；「停止发送」立即停。
5. **③ 板子控制**：降噪档位（旁路 / 轻量门 / RNNoise 三选一）、底噪注入
   （关 / 300 / 800 / 1500）、440 Hz 自检音。发完在「已发送」和日志里回显实际字节，
   板子串口会回显 `dsp=2 GATE` / `noise=300` 一行确认。
   > ✅ 这一版是**真机协议**：发到 **50507**、payload 只有 **1 字节**。
   > 早期版本的 `b"CTL"+码` 多字节帧发到 50506，固件根本没实现，所以按钮全都没反应——
   > 那些按钮（静音/音量±/自定义文本）已经删掉了，因为固件没有对应命令。
6. **④ 日志**：协议、声卡、发送结果、控制命令的文字记录，排错先看这里。

> 收和发可以同时开：先「开始收听」，再「发送测试音」，耳机口出声的同时 PC 也能听到麦克风。

## 板子控制命令（真机协议，**已对接**）

发到 `255.255.255.255:50507`，payload 就是 **1 个字节**，由 `udp_link.c` 的
`PORT_CTL` 分支解析：

| 字节 | 作用 | 幂等 |
| --- | --- | --- |
| `'0'` | 旁路（DSP 不处理） | ✅ |
| `'1'` | RNNoise（质量优先，带噪时 20.07 ms/帧 → 49 fps，会破碎） | ✅ |
| `'2'` | 轻量自适应噪声门（**默认档**，0.127 ms/帧，100 fps，稳态噪声 −23.7 dB） | ✅ |
| `'a'` / `'b'` / `'c'` / `'d'` | 注入合成底噪 0 / 300 / 800 / 1500 | ✅ |
| `'t'` | 440 Hz 自检音**翻转** | ❌ 唯一非幂等，别连按 |

例：切轻量门 → `32`；底噪 800 → `63`。

> ⚠️ 控制报文是**广播**，板子会收到 **2~3 份**。所以除 `'t'` 外所有命令都必须幂等——
> 早期用 `'n'` 做"循环档位"时，一次按键跳过两档，就是踩的这个坑。

下面这节 `b"CTL"` 帧格式是 PC 端早期拟定的**未采用方案**，代码里还留着（`pack_control` /
`BoardControl`）供自测与将来扩展，**真机不认**：

## 控制命令（早期 b"CTL" 帧，固件未实现）

发到 `255.255.255.255:50506`，独立格式，避免和音频包混淆：

| 偏移 | 长度 | 内容 |
| --- | --- | --- |
| 0 | 3 | 魔数 `b"CTL"` |
| 3 | 1 | 命令码：1=MUTE、2=UNMUTE、3=GAIN+、4=GAIN-、5=MODE、6=TEXT |
| 4 | 0/1/n | 参数：`MODE` 跟 1 字节模式号（0..3）；`TEXT` 跟 UTF-8 文本（≤32 字节） |

例：`MODE 3` → `43 54 4C 05 03`；`MUTE` → `43 54 4C 01`。

## 协议（PC 侧实现的就是这个）

UDP 载荷 = **8 字节头 + PCM**。

| 偏移 | 长度 | 内容 |
| --- | --- | --- |
| 0 | 1 | 魔数 `'A'` (0x41) |
| 1 | 1 | 魔数 `'U'` (0x55) |
| 2 | 2 | `seq`，帧序号，**大端 u16**，0..65535 回绕 |
| 4 | 2 | `chunk`，**大端 u16**，0 或 1 |
| 6 | 2 | `total`，**大端 u16**（见下方说明） |
| 8 | 960 | PCM：240 个立体声样本，小端 int16，每 4 字节 `[15:0]=左`、`[31:16]=右` |

- 一帧 = 480 个立体声样本 = 1920 字节 = 10 ms（48 kHz），拆成 2 个 UDP 包（每包 960 字节 PCM，
  总长 968 字节），100 帧/秒 → 200 包/秒，约 194 KB/s。
- **`total` 的坑**：协议文档写的是 480（样本数），但两块固件（`eth_audio/sw/udp_link.c`、
  `eth_axi/sw/udp_audio.c`）实际填的是 `AUDIO_BYTES = 1920`（字节数），而且板子收包时根本不看这个字段。
  所以本程序：**只透传、不校验 `total`**，重组只依赖 `chunk`；发送时默认填 480，可改；
  `selftest.py` 用 480 / 1920 / 0 三种值都测过。
- **必须发广播**：板子是裸 TEMAC + 手写 IPv4，**不实现 ARP 应答**。发单播的话 PC 先要 ARP，
  板子不回，包根本发不出去。所以目的地址用 `255.255.255.255`（程序默认值）；
  如果你的 PC 有多块网卡，要在「本地网卡 IP」里填 `169.254.191.246` 强制从对的那块出去。
- 板子收包判据很宽松：长度 ≥ 42、ethertype 0x0800、proto 17、**目的端口 50506**、
  载荷前两字节 `'AU'`。**不校验源端口、不校验 seq、不校验目的 IP**，所以从哪台机器发都能收。
- 板子不回 ARP、不回 ICMP —— **`ping 169.254.191.50` 不通是正常的**，别拿 ping 判断链路。

## 缓冲与漂移处理

板子用 48 MHz 晶振、声卡用另一个晶振，两者 0.1% 的偏差在 10 分钟里就是 ~600 ms 的累积误差，
必须主动修剪，否则延迟会一直涨到"说话后过几秒才听见"。

`JitterBuffer`（块粒度 10 ms，目标深度**自适应**）：

| 参数 | 值 | 行为 |
| --- | --- | --- |
| 目标深度 | 60~200 ms，默认 80 | 每 ≥1 s 调一次：`60 + 4 × 实测抖动`；只有本窗口出现欠载才向上抬（+20 起步），连续修剪才向下压（−10 起步）；死区 2 ms、**每 10 s 最多 ±20 ms**，不会来回震荡 |
| 温和修剪 | > 目标 + 25 ms | 每次 push 丢最旧的 1 块（10 ms），`trims += 1` |
| 溢出 | > 400 ms | 按样本裁回目标，`overflows += 1` |
| 欠载 / 丢帧 | 取不到数据 | 不再补纯静音：从断点样本做 **5 ms 指数淡出**，恢复时 **5 ms 淡入**，`underloads`/`concealed` 各 +1 |
| 时钟漂移 | 由到达间隔估 ppm | 按 `drift_ppm` 每秒最多删/插 **1 个样本**（`corrections`），把累积误差吃掉而不改变听感 |

- 抖动估计：到达间隔 `dt` 的 EMA（α=0.05），`jitter = Σ|dt−10ms|/n`；`drift_ppm = (10ms/dt̄ − 1)×1000000`。
- v1.1 自测实测：稳定流目标 82→62 ms；抖动流抬到 82 ms、单步 2.00 ms、无反向调整；
  ±0.5% 漂移跑 600 s 溢出 0 次、深度封顶 80 ms；+0.1% 漂移 600 s 最大深度 100 ms、修剪 55、溢出 0。
- 全安静时也不硬切：淡出/淡入的接缝跳变实测 0（自测用例 17），听感上只是"声音糊了一下"。

发送侧反过来：**不能突发补发**。固件的播放缓冲是 4 × 100 ms，`pb_wr` 回绕时不检查该块是否
正在播放，突发会把正在放的那块冲掉（爆音/卡顿）。所以 `BoardSender.play_array` 落后
超过 150 ms 时**重排时间基准**（`resyncs += 1`）而不是补发；开头先 prime 2 帧（200 ms）垫底。

## 排错

### 收不到包 / 一直是 0 帧

1. **目的端口和广播**：板子固定发 `255.255.255.255:50505`。PC 防火墙默认可能拦未知程序。
   临时放行：`New-NetFirewallRule -DisplayName "udp-audio-in" -Direction Inbound -Protocol UDP -LocalPort 50505 -Action Allow`
   （需要管理员；演示前先放行，比现场手忙脚乱强）。
2. **看「非法包」计数**：如果非法包在涨但帧数是 0，说明包收到了但格式不对——通常是
   固件改了头（`total`/`chunk` 语义），对照上文协议表检查。
3. **链路**：网线插 PL 那颗 PHY（YT8531C），不是 PS 那颗；PHY 协商强制 100M 全双工。
   板子不回 ARP/ICMP，`ping` 不通正常，用「已收帧」涨没涨来判断。
4. **多网卡**：笔记本同时有 WiFi 和直连网卡时，在「本地网卡 IP」填 `169.254.191.246`，
   否则广播可能从 WiFi 出去。

### 端口占用（50505 / 50506 已在用）

```powershell
netstat -ano | findstr :50505
netstat -ano | findstr :50506
# 找到 PID 后
taskkill /PID <pid> /F
```

常见原因：上一个实例没退干净、以前验证用的 Python 脚本还在跑。本程序收 50505 用
`SO_REUSEADDR`，两个实例不会抢端口失败，但会**随机分走帧**（表现是两边都卡），
所以只开一个。

### 有帧但没声音 / 爆音

- **选对声卡**：默认输出可能是 HDMI 或虚拟声卡。`python app.py --list-devices` 看编号，
  在界面里选「Realtek(R) Audio」那一路（MME / WASAPI 都行，WASAPI 延迟更低）。
- **别的程序独占 WASAPI**：某些播放器/会议软件独占后，`RawOutputStream` 会打不开，
  日志里会有 `打开播放流失败`，程序会退到 MME 或只统计不出声。
- **爆音/断续**：先看「欠载」和「目标/抖动」。目标深度会自己往 60~200 ms 之间调；
  欠载一直涨说明到达抖动比目标还大（或网络真丢包），可以先把 `JitterBuffer.ADAPT_MAX_MS`
  调大；溢出涨说明有突发堆积。现场别再手改参数，改完要重跑 `selftest.py`。
- **声音发闷/变调**：说明数据是 48 kHz 但在别的采样率播放——确认界面里没改动，
  程序固定 48 kHz。

### 波形/频谱不动

- 两个画布的数据来自**播放回调**，所以必须先「开始收听」并且播放流打开成功；
  只收包不播放（没声卡）时画布是平的。看日志有没有 `播放流已打开`。
- 静音时波形是一条平线、频谱柱子贴底，这是对的；柱顶的橙线是峰值保持，会慢慢掉。
- 窗口最小化时 Tk 不重绘，恢复窗口就继续动。

### 控制命令点了没反应

- 先看**端口**：必须是 **50507**，而且 payload 只有 **1 字节**。发到 50506 或发多字节
  `b"CTL"` 帧都会被固件当音频包丢掉（这是旧版本按钮失效的原因，已修）。
- 再看**板子串口**：点一下应该回显 `dsp=2 GATE` / `noise=300` 这样一行。
  串口没有回显 → 包没到（查网线口是否插在**靠电源开关**那个 RJ45、PC 速率是否 100 Mbps）。
- 想确认包真的出去了：Wireshark 过滤 `udp.port == 50507`，看载荷是不是单字节 `32`。

### 板子没声音（PC → 板子方向）

- 先看板子串口 `dac=` 是否每秒 +100。已实测：推 10 s 语音后 `dac` 从 12303 → 12353、
  `under=0`、`clob=0`，说明通路和缓冲都正常。
- PC 端能做的验证：日志里「发送结束：1000 帧 / 10.00 s」说明包确实发出去了。
- 耳机要插**板子**的 PHONE 口（R4=0x30 只开 LOUT1/ROUT1）；插 PC 的耳机孔听到的是
  麦克风上行流，不是 DAC 下行流。
- 目的地址别填成 `169.254.191.50`：板子不应答 ARP，单播发不出去，保持 `255.255.255.255`。
- 本地网卡 IP 填错（填了 WiFi 的地址）会导致包从错误的网卡出去，板子收不到。

## 已知限制

- 只支持 IPv4 广播/单播 UDP，没有重传、没有 FEC；丢包就是丢 10 ms 音频，靠抖动缓冲 + 淡出淡入掩盖。
- 播放固定 48 kHz 立体声 int16；A/B 增益只有 1.0× / 2.0× 两档（演示用），没有连续音量、不做响度归一化。
- 波形是 2 s 窗、每列 min/max（不是每个采样都画）；频谱是 L/R 混单声道后的幅度谱，
  未做校准，柱高只表示相对强弱，不是 dB SPL。
- 录音只写 48 kHz / 16 bit / 2 ch PCM（就是播放链里的字节，增益和补的静音都会录进去）。
- **板子控制已对接真机协议**（单字节 → 50507），界面上点一下，板子串口立即回显
  `dsp=`/`noise=`。代码里保留的 `b"CTL"` 帧格式只是历史遗留 + 扩展位，真机不认。
- WAV 只读 PCM（8/16/24/32 bit），不支持浮点 WAV / 压缩格式。
- 发送不重发、不补帧：网络抖动靠板子 4 × 100 ms 缓冲吸收。

## v1.2：延迟档位 + 基音外推（2026-10-26 晚）

### 三档延迟（界面上「延迟档位」下拉框，运行中即时生效）
| 档位 | 目标深度 | 什么时候用 |
| --- | --- | --- |
| `auto 自适应 60~200 ms` | 由实测抖动推（`60 + 4×抖动`） | 默认，常规演示 |
| `low 低延迟 45~90 ms` | 夹在 45~90 | 网络干净、要"像直连"的感觉 |
| `stable 稳定 110~220 ms` | 夹在 110~220 | 现场 WiFi/交换机抖动大，宁慢不卡 |

切档只改目标的上下限，当前深度仍按 2 ms/s 平滑移动，所以**切的时候不会听到突变**。
`snapshot()` 新增 `mode / mode_min_ms / mode_max_ms`。

### 丢包隐藏升级：从"淡出"到"延续基频"
旧行为是丢帧时把最后一段做 5 ms 指数淡出（听起来是"断一下就没了"）。现在是 WebRTC NetEq `expand`
的简化版：用 FFT 自相关在 **80~800 Hz** 找基音周期（取"相关度达最大值 92% 里最短的那个"避免 440 Hz
被认成 220 Hz 的倍周期错误），把一个周期拼接到空洞里，并按 **60 ms 时间常数**衰减 —— 短丢包
（<30 ms）几乎听不出接缝，长丢包会自然减弱而不是一直"嗡嗡"重复。找不到可信周期时自动退回淡出。

`snapshot()` 新增 `pitch_hz / extrapolated`，界面在「延迟档位」右边实时显示当前基音与外推次数。

# 技能包：端侧音频链路的"能复现"工作流

这不是一份功能介绍，是一套**可复用、可验证、有失效边界**的做法。每一条都从本工程的一次真实失败里提炼，并注明"什么情况下它不管用"——否则它只是一句正确的废话。

> 配套材料：开发过程中使用 **AMD Ross™ 智能体辅助设计套件**（MCP 驱动 Vivado/Vitis/xsdb + AMD 知识库 + agent skills）踩到的 20 个具体问题、根因与规避动作，逐条记在
> [`../docs/amd_ross_agent_notes.md`](../docs/amd_ross_agent_notes.md)。本文的 S1–S5 是那 20 条里被验证可复用的部分，其余（工具细节类）留在那份笔记里备查。
> 另外，本文件的技能命名与 AMD Ross 的 agent skill 格式一致：一条技能 = 适用场景 + 怎么用 + 什么时候不灵，写成 markdown 就能被别人（或别的 agent）直接调用。

## 0. 技能是怎么提炼出来的

| 失败 | 当时怎么想的 | 提炼出的技能 | 怎么验证它有效 |
|---|---|---|---|
| 重新综合后 0 包，反复三天 | 以为是 RTL 改动引入的 bug，逐个模块回退 | **先量"这个域有没有约束"，再量"逻辑对不对"**（S1） | 用 `check_timing` 的 `no_clock` 计数定位到 16923 个无约束触发器；补约束后重建 3 次全部 100 fps |
| 看到"有数据"就以为链路通 | 用采样率很低的探针看 `tvalid`，得出"有波形"的错误结论 | **占空比探针法则**：占空比 < 1 % 的"有信号"等于没有 | 把 `m_axis_tvalid` 占空比从 1/1000 判为"恒低"，与 `remain empty=1` 自洽 |
| 换了 5 个版本的 TTS 仍"AI 味重" | 以为是参数没调好 | **区分"参数问题"与"模型天花板"**（S2） | 同一句话用 4 个音色 × 3 组参数交叉测，结论是音色层决定，参数只改语速感 |
| 视频提示词给了 45 s，用户要 2:30 | 以为需求是"做个短视频" | **先问交付形态，再写第一行**（S3） | 之后每个修订版都先复述"时长/比例/交付物"再动笔，返工率归零 |
| 文档里写了 `bclk 3.072 MHz` | 抄了端口注释 | **注释不是事实，分频器才是事实**（S4） | 用 `bclk_div_cnt == 8'd3` 反推 650.8 ns，与 32 BCLK/帧 × 48 kHz 自洽 |
| `res[]` 调试表读数是死的 | 以为固件在更新 | **"两次读数相同"就是"这个读数没在更新"**（S5） | 连读两次比对，发现全等 ⇒ 改看 50508 状态包 |

## 1. S1：先查约束，再查逻辑

**适用场景**：工程"以前能跑、重新实现就坏"，或者现象是"全 0 / 全不动 / 恒高恒低"这种边界值。

**用法**（每次重新实现后按顺序跑，30 秒内出结论）：

```powershell
# 1) 有没有域没被约束
Select-String -Path impl_1\*timing_summary_routed.rpt -Pattern "no_clock" -Context 0,4
#    看 no_clock 的数字和它下面的 root clock pin。大于 100 就是有事。

# 2) 非时钟时序单元（TIMING-17）
Select-String -Path impl_1\*timing_summary_routed.rpt -Pattern "Non-clocked sequential cell"

# 3) 这个域的时钟有没有上 BUFG（上了 BUFG 但没 create_clock 最坑）
Select-String -Path impl_1\*clock_utilization_routed.rpt -Pattern "<那个寄存器名>"

# 4) 有没有 RAM 被拆成触发器（Synth 8-4767 / 8-13159）
Select-String -Path *synth*\runme.log -Pattern "8-4767|8-13159"
```

**判据**：`no_clock > 100` 或 `TIMING-17 > 0` ⇒ **先把约束补齐再谈逻辑**，此时任何"改了 RTL 就好了"的结论都不可信（可能只是布局重新抽签抽中了）。

**失效条件**：设计里确实存在"故意不受约束"的逻辑（例如纯异步握手、LED 心跳）。这种情况下要把它们显式 `set_false_path` 掉，否则这个判据永远为真、失去意义。本工程的 LED 心跳就是这类，写约束时按名字排除。

## 2. S2：参数问题还是天花板问题

**适用场景**：任何"效果不够好，看起来再调调就行"的主观评价（音色、画质、识别率）。

**用法**：做一次 2×N 的交叉表——**换模型/音色** vs **只调参数**。

本工程的表（同一句话，29 字）：

| 音色 | 原速 | +8%/+25Hz | +12%/+45Hz |
|---|---|---|---|
| 晓伊 | 6.74 s | 6.24 s | 6.02 s |
| 晓臻（台湾腔） | 7.20 s | — | 6.94 s |
| 晓晓 | 6.41 s | — | — |

**判据**：如果换音色造成的差异 >> 调参数造成的差异，就是**天花板问题**，继续调参数是浪费；要换模型（本地训音色）或者换表达方式（改成不用旁白）。

**失效条件**：当差异落在主观区间（"有点AI味"vs"没那么重"）且没有客观指标时，这个表只能定方向、不能定结论。本工程最后的选择是**不用合成语音**——这是这张表逼出来的决定，不是妥协。

## 3. S3：先问交付形态，再写第一行

**适用场景**：所有"帮我做个 X"的模糊需求（视频、文档、界面）。

**用法**：动笔前必须确认四件事，缺一件就先问：

1. **时长/篇幅**（45 秒还是 3 分钟？）
2. **比例/格式**（16:9？A4？docx 还是 pdf？）
3. **交付物**（一个文件？一个目录？能直接粘的文本？）
4. **谁来看**（评委？同事？机器？）

**判据**：这四项里任何一项答错，返工成本 ≥ 重做一遍。本工程 45 s → 2:43 的返工就是因为跳过了第 1 项。

**失效条件**：探索性任务（"先看看能做成什么样"）不该问这四项，应该先给最小可看的东西。区分标准：用户说"大概"= 探索；用户说"交到 XX" = 交付。

## 4. S4：注释不是事实

**适用场景**：写约束、写文档、写指标时引用任何"看起来权威"的常量。

**用法**：常量必须能**从代码反推并自洽**。三个独立来源对不上时，以**能自洽的那两个**为准，并留一行注释说明为什么改了。

本工程的例子：

| 来源 | 值 | 是否可信 |
|---|---|---|
| 端口注释 | "aud_bclk 3.072 MHz" | ✗ 抄错了 |
| 分频器代码 `bclk_div_cnt == 8'd3` | 8 × 81.35 ns = 650.8 ns → 1.536 MHz | ✓ |
| 帧结构自洽（32 BCLK/帧 × 48 kHz） | 1.536 MHz | ✓ |

**失效条件**：当两个来源都"看起来自洽"时，必须做一次实测（示波器/ILA），不能靠推理定输赢。

## 5. S5：读数是否在动，比读数是多少更重要

**适用场景**：任何一个"状态寄存器"、"计数"、"帧号"。

**用法**：**同一次会话里连读两次，比对是否相同**。相同 = 这个读数不反映实时状态（可能是常量、可能是被覆盖、可能是别的版本写的）。

本工程踩了两次：`cnt_rx_push` 两次都是 `0x008B1022`（真的冻结）、`res[0..15]` 两次全等（这个寄存器早就不更新了）。前者是 bug 证据，后者是文档过期的证据——**只看一次读数会把两者混为一谈**。

**失效条件**：低频事件（每分钟一次的状态）连读两次也会相同。要么拉长间隔，要么直接看"有没有单调递增的字段"（帧号/序号）。

## 6. 案例模板

### 6.1 约束补丁模板（给"重建就坏"这一类问题）

```tcl
# --- 音频采集域：由 slave_signal_gen 分频产生，必须显式定义 ---
# 周期由 slave_signal_gen.v:65 的 bclk_div_cnt == 8'd3 反推：8 × 81.354 ns
create_clock -name aud_bclk_pl -period 650.800 [get_pins {u_bd/eth_audio_i/audio_axis_core_0/inst/u_slave_signal_gen/aud_bclk_reg/Q}]
create_clock -name aud_lrc_pl  -period 20833.333 [get_pins {u_bd/eth_audio_i/audio_axis_core_0/inst/u_slave_signal_gen/aud_lrc_reg/Q}]

# 两组时钟异步：主系统时钟组 vs 音频域
set_clock_groups -asynchronous \
  -group [get_clocks -include_generated_clocks {clk_fpga_0 clk_fpga_1}] \
  -group [get_clocks {aud_mclk_OBUF aud2_mclk_OBUF aud_bclk_pl aud_lrc_pl}]

# LRC → BCLK 是"同一 mclk 沿同时翻转"的伪同步关系：
# 不许当作普通同步路径分析（会误报），按数据路径给上限
set_max_delay -datapath_only -from [get_clocks aud_lrc_pl] -to [get_clocks aud_bclk_pl] 20.000
```

### 6.2 A/B 实验模板（给"到底是哪个变量起作用"这一类问题）

```
变量：<只写一个>
不变量：比特流哈希、固件哈希、PC 侧脚本、输入信号（同一段录音文件）
测量：<一个可量化指标>，重复 <n> 次，报中位数与极差
结论句式：在 <条件> 下，<变量> 使 <指标> 从 <A> 变为 <B>（n=<次>）
```

### 6.3 "诚实字段"模板（给"功能没接上但界面要显示"这一类问题）

宁可显示 `未生效`，也不要显示一个看起来成功的值：

```
dac_mode == 3  ⇒  界面显示"未生效（这块 bit 里没有 dac_split）"
```

判据：**用户能不能靠这个字段发现"我操作了但没反应"**。不能，就说明这个字段在骗人。

## 7. 校验脚本

随包提供两个可直接运行的自检：

```powershell
# 交付包结构自检：中文路径、必需文件、metrics 表头、docx 是否可打开
python skill\scripts\check_delivery.py <包根目录>
```

两个脚本都只读、不改任何文件，输出 `PASS/FAIL` 行，失败时给出具体文件与行号。

## 8. 踩坑清单（15 条，按踩到的顺序）

| # | 坑 | 正确做法 |
|---|---|---|
| 1 | 只看一次读数就下结论 | 连读两次比对（S5） |
| 2 | 相信端口注释里的频率 | 从分频器代码反推（S4） |
| 3 | 重新实现后不查 `no_clock` | 每次实现后先跑 S1 的四条 |
| 4 | 把"示波器上有波形"当成"有数据" | 看占空比，< 1 % 视为无 |
| 5 | 综合日志的 WARNING 不看 | `8-4767 / 8-13159 / 8-7137` 必须逐条读 |
| 6 | 用单播给板子发控制包 | 必须广播到 `169.254.255.255` |

## 9. 这套技能的边界（明确不适用的情况）

1. **不适用于首次设计**：S1 假设"已经有过一个能跑的实现"。全新设计应从约束规划开始，而不是从"查有没有漏约束"开始。
2. **不适用于纯软件项目**：S1/S4 的判据（`no_clock`、分频器）是 FPGA 专有的。
3. **S2 不能替代客观指标**：交叉表只能定方向；要下结论必须有 SNR/THD/字错率这类数。
4. **S3 的四问会打断探索**：用户还在试想法时不要问，先给东西看。
5. **本套技能没有覆盖"多人协作"**：本工程是单人 + AI 助手，协作冲突场景未验证。
